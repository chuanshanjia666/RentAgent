## 一、测试范围与分层策略

单元测试只覆盖**不依赖外部进程**的逻辑：状态机、权限归属、金额与日期计算、文本解析、加解密、参数约束。
凡属"必须真连 MySQL / Redis / 网络才能验证"的行为（唯一键约束、逻辑删除、`JSON_CONTAINS` 检索、聚合 SQL、
验证码 TTL、模型流式输出）不在本层做假测试，统一交给《测试用例设计》的集成层，
避免用 Mock 造出与真实语义不符的"绿色假象"。

| 层次 | 手段 | 依赖 | 用例数 | 执行命令 |
| ---- | ---- | ---- | ------ | -------- |
| 后端单元测试 | JUnit 5 + Mockito 打桩 Mapper 与模型调用层 | 无（不连库/缓存/网络） | **161** | `cd server && mvn test` |
| 前端单元测试 | vitest + jsdom | 无（假 `fetch`/`ReadableStream`） | **22** | `cd frontend && npm test` |
| 集成与端到端 | 真实 MySQL 8 + Redis + 运行中后端 + **真实大模型** | 全栈 | **125 条断言** | `bash scripts/ci-smoke.sh` |
| 反向门禁（无模型必须报错） | 无凭据实例 + 接口探针 | 全栈 | **6 条断言** | `bash scripts/ci-no-model-check.sh` |

其中后端 161 条 = 既有 9 条（`AiPropsTest` 6、`OpenAiResponsesChatModelTest` 3）+ 本次新增 **152 条**；
前端 22 条全部为本次新增。

### 1.2 测试替身的使用边界

| 替身对象 | 处理方式 | 理由 |
| -------- | -------- | ---- |
| MyBatis-Plus Mapper | Mockito `@Mock` 打桩 | 单测不校验 SQL，只校验"是否发起正确的调用与状态迁移" |
| `AuthService.realnamePassed` | Mockito 打桩 | 隔离 FR-03 依赖，专测 FR-05 的实名校验分支 |
| `StringRedisTemplate` | Mockito 打桩（含 `opsForValue()` 链） | 验证键名、写入值、TTL 与失败计数语义 |
| BCrypt / AES / SHA-256 | **真实实现** | 加密强度与格式属于被测行为，不能替身 |
| `NotificationService` | Mockito 打桩 | 验证"该不该发、发给谁、什么类型" |
| `AiJsonClient`（结构化模型调用层） | Mockito 打桩（返回固定结构 / 抛 4001） | 让四项 AI 分析可在无网络下验证"送模型的数据"与"模型返回的校验" |
| `LlmGateway` + `ChatLanguageModel` | Mockito 打桩（固定文本/异常） | 覆盖 JSON 提取、解析失败重试、未配置模型硬报错 |
| 数据库唯一键冲突 | `thenThrow(new DuplicateKeyException(...))` | 单测无法造唯一键，只能注入其异常以验证业务码映射 |
| 前端 `fetch` / `ReadableStream` | `vi.stubGlobal` + 内存流 | 精确控制分片边界（半行缓冲）与失败分支 |
| 前端 `localStorage` | 测试内内存版 Storage 实现 | vitest 的 jsdom 环境不注入 `localStorage` |
| `window.RentAgent`（桌面端注入点） | `vi.stubGlobal` + `vi.resetModules()` 后动态导入 | 模块级读取注入值，需按用例重建模块 |

### 1.3 一个必要的测试基础设施

纯 Mockito 单测没有 MyBatis 容器初始化实体缓存，一旦被测代码需要**渲染 lambda 列名**
（`LambdaUpdateWrapper.set(...)`、`Wrapper.getSqlSegment()`，如房源评分回填、订单/合同列表过滤条件），
MyBatis-Plus 会抛 `can not find lambda cache for this entity`。
`support/EntityMetadataHelper` 按需调用 `TableInfoHelper.initTableInfo(...)` 注册实体元数据，
使这些断言可以校验真实列名（如 `tenant_id = ?`），而不是绕开验证。

## 五、首轮执行发现的缺陷

| 编号 | 严重度 | 位置 | 现象 | 根因 | 处理 |
| ---- | ------ | ---- | ---- | ---- | ---- |
| BUG-01 | 中（功能缺陷，不涉数据泄漏） | `common/CryptoUtil.java` `decrypt` | 身份证号解密恒失败；受其影响 `GET /users/me/realname` 返回的 `maskedIdCard` 恒为 `****`（`AuthService.mask` 捕获异常后兜底） | GCM 参数构造把**密文**当成了 IV（`new GCMParameterSpec(128, all, 12, all.length-12)` 的 offset/len 语义是 IV 的位置与长度），且 `doFinal(all)` 又把 IV 一并当作密文，必然 `AEADBadTagException: Tag mismatch` | 已修复：IV 取前 12 字节、`doFinal(all, 12, len-12)`；回归用例 `UT-CRYPTO-01/02/04/06`、`UT-AUTH-12`，集成层 `IT-09-05` |

> 说明：该缺陷此前未被发现的原因是加密**写入**正常、且 `decrypt` 只有脱敏展示一个调用点，
> 异常被兜底文案掩盖；单测以真实密钥驱动加解密往返后立即暴露。

| 编号 | 严重度 | 位置 | 现象 | 根因 | 处理 |
| ---- | ------ | ---- | ---- | ---- | ---- |
| BUG-02 | 高（AI 能力实际失效） | `LlmAgent`（流式编排） | 客服/合同场景下模型只回一句过程语（实测 15 字"我先为您查询平台押金相关规定。"），**工具从未被调用**，因而没有检索结果、没有知识库来源（`citations` 为空），用户拿不到有效回答 | 部分模型聚合网关的**流式**响应会在模型叙述句之后被截断，`tool_calls` 事件丢失（LangChain4j 因此不执行工具、直接结束本轮）；旧实现的重试只覆盖找房场景且仍走流式，同样会被截断 | 已修复：新增"按场景判断是否应调用工具却未调用"的检测（找房看回答长度、客服/合同看是否有知识库引用），命中则以**非流式**方式重跑一次（同一 Agent、同一会话记忆）后切片回放；回归用例 `UT-AIJSON-*` + 集成 `IT-9-10~12` |

> BUG-02 的意义：它在"还没有真实模型"的阶段无法被发现（规则引擎自己会调工具），
> 是本次切换到真实模型后由集成冒烟**首次暴露**的通道级缺陷。
