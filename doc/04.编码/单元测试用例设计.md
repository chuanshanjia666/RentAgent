## 一、测试范围与分层策略

单元测试只覆盖**不依赖外部进程**的逻辑：状态机、权限归属、金额与日期计算、文本解析、加解密、参数约束。
凡属"必须真连 MySQL / Redis / 网络才能验证"的行为（唯一键约束、逻辑删除、`JSON_CONTAINS` 检索、聚合 SQL、
验证码 TTL、模型流式输出）不在本层做假测试，统一交给《测试用例设计》的集成层，
避免用 Mock 造出与真实语义不符的"绿色假象"。

| 层次 | 手段 | 依赖 | 用例数 | 执行命令 |
| ---- | ---- | ---- | ------ | -------- |
| 后端单元测试 | JUnit 5 + Mockito 打桩 Mapper 与模型调用层 | 无（不连库/缓存/网络） | **190** | `cd server && mvn test` |
| 前端单元测试 | vitest + jsdom | 无（假 `fetch`/`ReadableStream`） | **26** | `cd frontend && npm test` |
| 集成与端到端 | 真实 MySQL 8 + Redis + 运行中后端 + **真实大模型** | 全栈 | **130 条断言** | `bash scripts/ci-smoke.sh` |
| 反向门禁（无模型必须报错） | 无凭据实例 + 接口探针 | 全栈 | **6 条断言** | `bash scripts/ci-no-model-check.sh` |

其中后端 190 条 = 既有 9 条（`AiPropsTest` 6、`OpenAiResponsesChatModelTest` 3）+ 首轮新增 152 条 + 次轮新增 17 条 + 三轮新增 **9 条**（`UT-OPENAI-12~15` 4 条 + `UT-AGENT-01~05` 5 条）、删除 1 条（`UT-HOUSE-17`），净增 8 条
（协议适配器 10、Schema 生成 4、结构化输出分支 3）+ 代码评审回归 **4 条**
（过去时间不可预约、编辑不改动图片、SSE 分片解析失败终止、非参数类 4xx 不降级）；
前端 26 条 = 既有 22 条 + 本轮新增 **4 条**（FT-SSE-07~10：末尾缓冲补刷、终止回调兜底、流中断可读报错、主动中断静默）。

### 1.2 测试替身的使用边界

| 替身对象 | 处理方式 | 理由 |
| -------- | -------- | ---- |
| MyBatis-Plus Mapper | Mockito `@Mock` 打桩 | 单测不校验 SQL，只校验"是否发起正确的调用与状态迁移" |
| `AuthService.realnamePassed` | Mockito 打桩 | 隔离 FR-03 依赖，专测 FR-05 的实名校验分支 |
| `StringRedisTemplate` | Mockito 打桩（含 `opsForValue()` 链） | 验证键名、写入值、TTL 与失败计数语义 |
| BCrypt / AES / SHA-256 | **真实实现** | 加密强度与格式属于被测行为，不能替身 |
| `NotificationService` | Mockito 打桩 | 验证"该不该发、发给谁、什么类型" |
| `AiJsonClient`（结构化模型调用层） | Mockito 打桩（返回固定结构 / 抛 4001） | 让四项 AI 分析可在无网络下验证"送模型的数据"与"模型返回的校验" |
| `LlmGateway` + `ChatLanguageModel` | Mockito 打桩（固定文本/异常） | 覆盖 JSON 提取、解析失败重试、未配置模型硬报错 |
| `JsonSchemaChatModel`（结构化输出能力） | Mockito 打桩（返回 JSON / 抛 4xx 或超时） | 覆盖"优先 json_schema、端点拒绝后降级、偶发失败不降级"三个分支 |
| SSE 分片文本 | 真实解析（喂入构造的分片，不打桩） | 流式解析是被测行为：须验证"正文与工具调用同轮并存"不丢失 |
| 数据库唯一键冲突 | `thenThrow(new DuplicateKeyException(...))` | 单测无法造唯一键，只能注入其异常以验证业务码映射 |
| 前端 `fetch` / `ReadableStream` | `vi.stubGlobal` + 内存流 | 精确控制分片边界（半行缓冲）与失败分支 |
| 前端 `localStorage` | 测试内内存版 Storage 实现 | vitest 的 jsdom 环境不注入 `localStorage` |
| `window.RentAgent`（桌面端注入点） | `vi.stubGlobal` + `vi.resetModules()` 后动态导入 | 模块级读取注入值，需按用例重建模块 |

### 1.3 一个必要的测试基础设施

纯 Mockito 单测没有 MyBatis 容器初始化实体缓存，一旦被测代码需要**渲染 lambda 列名**
（`LambdaUpdateWrapper.set(...)`、`Wrapper.getSqlSegment()`，如房源评分回填、订单/合同列表过滤条件），
MyBatis-Plus 会抛 `can not find lambda cache for this entity`。
`support/EntityMetadataHelper` 按需调用 `TableInfoHelper.initTableInfo(...)` 注册实体元数据，
使这些断言可以校验真实列名（如 `tenant_id = ?`），而不是绕开验证。

### 3.3 FT-SSE AI 对话流式解析（FR-12/NFR-02）— `api.test.ts`，12 条

| 编号 | 被测规则 | 预期 |
| ---- | -------- | ---- |
| FT-SSE-01 | delta/done 事件 | delta 按到达顺序逐字回调，done 收尾并携带 messageId/引用/时延 |
| FT-SSE-02 | 半行缓冲 | 单条事件被拆到多个网络分片时仍正确拼装（流式渲染不花屏） |
| FT-SSE-03 | 容错 | 注释行、非 `data:` 行、坏 JSON 行被忽略且不中断流 |
| FT-SSE-04 | 后端返回业务错误（非事件流，如未配置模型的 4001） | 解析 JSON 响应体并把后端 message 透出给用户，不触发 delta |
| FT-SSE-04b | 非事件流且响应体非 JSON | 退回状态码提示 `连接智能助手失败（502）` |
| FT-SSE-04c | 流中出现 `{"error":…}` 载荷 | 回调错误原因，且不触发 delta/done（模型调用失败不伪造回答） |
| FT-SSE-05 | 网络异常 | 回调「网络连接失败」且 Promise 正常结束（不抛未捕获异常） |
| FT-SSE-06 | 请求构造 | URL 含版本前缀 `/api/v1`、携带 Bearer JWT 与 JSON 头 |
| FT-SSE-07 | 末尾缓冲补刷 | 最后一帧不带换行符时事件仍被处理（否则 done 丢失） |
| FT-SSE-08 | 终止回调兜底 | 服务端未发终止事件时也回调 done，界面不会永远停在「回复中…」 |
| FT-SSE-09 | 流中途断开 | 回调「连接中断，请重试」，Promise 正常结束而不抛未捕获异常 |
| FT-SSE-10 | 主动中断 | 传 `AbortSignal` 中断（切换会话）时 delta/done/error 均不触发，不误报网络错误 |

## 五、首轮执行发现的缺陷

| 编号 | 严重度 | 位置 | 现象 | 根因 | 处理 |
| ---- | ------ | ---- | ---- | ---- | ---- |
| BUG-01 | 中（功能缺陷，不涉数据泄漏） | `common/CryptoUtil.java` `decrypt` | 身份证号解密恒失败；受其影响 `GET /users/me/realname` 返回的 `maskedIdCard` 恒为 `****`（`AuthService.mask` 捕获异常后兜底） | GCM 参数构造把**密文**当成了 IV（`new GCMParameterSpec(128, all, 12, all.length-12)` 的 offset/len 语义是 IV 的位置与长度），且 `doFinal(all)` 又把 IV 一并当作密文，必然 `AEADBadTagException: Tag mismatch` | 已修复：IV 取前 12 字节、`doFinal(all, 12, len-12)`；回归用例 `UT-CRYPTO-01/02/04/06`、`UT-AUTH-12`，集成层 `IT-09-05` |

> 说明：该缺陷此前未被发现的原因是加密**写入**正常、且 `decrypt` 只有脱敏展示一个调用点，
> 异常被兜底文案掩盖；单测以真实密钥驱动加解密往返后立即暴露。

| 编号 | 严重度 | 位置 | 现象 | 根因 | 处理 |
| ---- | ------ | ---- | ---- | ---- | ---- |
| BUG-02 | 高（AI 能力实际失效） | `LlmAgent`（流式编排）→ 协议适配器 | 客服/合同场景下模型只回一句过程语（实测 15 字"我先为您查询平台押金相关规定。"），**工具从未被调用**，因而没有检索结果、没有知识库来源（`citations` 为空），用户拿不到有效回答 | **首轮定位有误**：初判为聚合网关的流式响应在叙述句之后截断、丢失 `tool_calls`。本轮以原始 SSE 抓包复核，网关流式分片**完整**（含 `tool_calls` 与 `finish_reason:\"tool_calls\"`），真实根因在客户端：langchain4j 0.35 的流式响应组装器（`OpenAiStreamingResponseBuilder.build()`）在累积正文非空时直接返回纯文本消息、**丢弃全部 tool_calls**（字节码层确认），而该模型恰好"先叙述再调工具"，于是流式轮次退化为一句过程语，工具永不执行（同步调用走另一条解析路径，故当时"非流式重跑"看起来有效） | 已修复：① openai-chat-completions 协议改由自研适配器 `OpenAiChatCompletionsModel` 实现，正文与 `tool_calls` 分别累积后合并为一个消息（三种协议全部自研，移除 langchain4j-open-ai 依赖）；② 非流式兜底收窄为"本轮未执行任何工具且回答不像结论"，工具已执行的短回答不再重跑。回归用例 `UT-OPENAI-06`（同轮并存）+ 集成层"模型实际调用了 searchHouses / searchKnowledge"两条断言 |

> BUG-02 的意义：它在"还没有真实模型"的阶段无法被发现（规则引擎自己会调工具），
> 是本次切换到真实模型后由集成冒烟**首次暴露**的缺陷。
> 更值得记录的是**首轮根因定位错了**：当时手头只有"工具没被调用"这一现象，
> 便归因于聚合网关截断（并据此加了非流式兜底，掩盖了症状）；本轮抓取原始 SSE 分片逐条比对，
> 才把根因锁定在客户端解析。教训：涉及第三方通道的缺陷，先取原始报文，再下结论。
