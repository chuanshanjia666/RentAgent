## 二、总体设计

### 2.1 设计原则

1. **需求驱动**：每个设计单元均可追溯到 FR/NFR 编号，与《需求跟踪矩阵》双向对应；
2. **分层解耦**：表现层、业务层、智能体层、数据层职责单一，智能体层与业务层通过"工具接口"解耦（NFR-09 可插拔）；
3. **保 MVP、分级交付**：架构首先保障 P0 闭环（注册登录 → 发布房源 → 审核 → 检索 → AI 找房 → 智能客服 → 预约 → 签约），P1/P2 在同一架构上增量扩展；
4. **风险前置**：大模型 API 不稳定（风险 R1）用网关层隔离；AI 幻觉（风险 R2）用 RAG 强制引用 + 免责声明兜底。

### 2.2 架构风格说明（应用项目 vs 嵌入式项目）

本项目为典型的**应用项目（B/S 架构）**，采用"前后端分离 + 四层架构"；课堂上讲解的嵌入式项目架构以"感知层（传感器采集）— 控制层（MCU/RTOS 实时处理）— 执行层（驱动执行机构）+ 云端联动"为主线，关注实时性与资源受限。两者对比：

| 维度 | 应用项目（本项目） | 嵌入式项目 |
| ---- | ------------------ | ---------- |
| 交互方式 | 浏览器 HTTP(S)/SSE 请求响应 | 传感器/执行器物理信号交互 |
| 分层主线 | 表现层 → 业务层 → 智能体层 → 数据层 | 感知层 → 控制层 → 执行层（→ 云端） |
| 关键指标 | 并发、响应时间、可维护性 | 实时性、功耗、内存占用 |
| 数据设计 | 关系库 + 缓存 + 向量库 | 嵌入式数据库/文件/消息队列 |

RentAgent 中不存在设备侧感知与实时控制环节，故不引入嵌入式分层；仅 AI 对话采用 SSE 流式输出以满足"首字 ≤ 3s"的准实时体验（NFR-02）。

### 2.4 技术选型（按《项目最终确认书》基线）

| 层次 | 选型 | 设计要点 |
| ---- | ---- | -------- |
| 表现层 | React 18 + TypeScript + Vite + Ant Design 5 + ECharts | 三端单仓单应用，react-router 哈希路由按角色分区；Context 管登录态；AI 对话为 SSE 流式渲染；strict 模式类型检查（`tsc --noEmit && vite build`）。客户端两种分发形态共用同一份构建产物：Web 版由 Nginx 托管静态资源（构建基址为相对路径，可部署在任意子路径）；桌面端由 Electron 外壳直接加载该产物（`electron/`，仅注入后端地址与窗口参数，不加界面与功能） |
| 后端 | Spring Boot 3.x + MyBatis-Plus + spring-security-crypto | Controller-Service-Mapper 分层；鉴权为自研 JWT 过滤器 + `@RequireRole` 角色拦截器（BCrypt 取自 spring-security-crypto）；springdoc-openapi 自动生成 Swagger 文档（NFR-08） |
| 智能体框架 | LangChain4j | Function Calling、ChatMemory、RAG（EmbeddingStore）工程化封装，Spring Boot starter 集成 |
| 大模型 | **模型无关**：LLM 网关按协议适配任意兼容模型——openai-chat-completions（最通用；厂商端点与聚合网关多兼容此协议）/ anthropic-messages（Anthropic 原生）/ openai-responses（OpenAI 新接口） | 端点、模型、API Key 全部可配置，`AI_BACKEND` 一键切换命名后端，**换模型/换供应商只改配置、不改代码**；无有效 Key 时 AI 能力统一报 4001（风险 R1 应对，不做规则/模拟兜底）。三种协议均为本项目自研适配器：openai-chat-completions 与 anthropic-messages 的适配器把同一轮内的正文与工具调用分别累积后合并（模型普遍"先叙述再调工具"，否则工具不会被执行），anthropic-messages 适配器还可跳过兼容端点的思维链块并关闭 thinking 以降低首字延迟。**流式分支显式校验 HTTP 状态码并剥离 `CompletionException` 外壳**：非 2xx 的响应体是错误 JSON 而非 SSE，不判状态码就会被当成“模型没说话”；**响应既无正文也无工具调用时按失败上报，绝不伪造回答**（典型成因是推理内容占满 `max_tokens`）；单轮 token 上限默认 4096（实测一轮约 1.6k~2.0k tokens，取值过紧即被 `finish_reason=length` 截断）。当前演示通道经模型聚合网关接入 `deepseek/deepseek-v4.1-flash` |
| 数据库 | MySQL 8（InnoDB，utf8mb4） | 18 张业务表，详见《数据库设计简介》 |
| 缓存 | Redis 7 | 验证码、登录失败计数、JWT 黑名单、热点房源缓存、AI 热会话上下文 |
| 向量检索 | Redis Stack（RediSearch，部署就绪） | 向量索引为 RAG 升级预留位（`kb_chunk.vector_ref`）；首版知识库检索走关键词命中 + 计分 |
| 鉴权安全 | JWT + RBAC + BCrypt + AES | 三角色简化 RBAC（角色字段 + 方法级注解鉴权），敏感字段加密（NFR-03/04） |
| 部署 | Docker Compose 单机 | nginx / server / mysql / redis-stack 四容器，一键拉起演示环境；桌面端以安装包（AppImage / deb）单独分发，运行需能访问后端服务 |

### 3.2 模块职责与设计要点

| 模块 | 覆盖需求 | 后端组件（包） | 关键设计要点 |
| ---- | -------- | -------------- | ------------ |
| 用户与权限 | FR-01~04 | `auth`、`user` | 注册即选角色；JWT 无状态登录 + Redis 失败计数（5 次锁 10 分钟）；禁用即时生效由每请求的用户状态校验保证；RBAC 三角色 `@RequireRole` 注解鉴权；实名信息 AES 加密存储（FR-03） |
| 房源管理 | FR-05~08 | `house` | 状态机：待审核 → 已通过/已驳回 → 已上架 → 已下架/已出租；编辑后回退待审核；仅"已通过且上架"进入检索域；图片上传后校验类型/大小；首图同步写入 `house.cover_url` 冗余列（列表卡片与预约 VO 只读该列，避免逐条回表取图）；编辑请求未携带 `images` 字段时视作"本次不改动图片"（传空数组才是显式清空）；FR-08 识别结果走 `ai_analysis` 异步回填 |
| 检索与推荐 | FR-09~11、FR-25 | `search`、`favorite` | MySQL 组合索引 + LIKE 前缀匹配支撑关键词；筛选条件动态 SQL；地图找房按 lng/lat 范围查询（FR-10）；推荐 = 收藏/浏览行为加权 + Redis ZSet 热度榜（FR-11）；收藏唯一约束（FR-25） |
| AI 智能体服务 | FR-12~16 | `agent`（智能体层） | 详见第四章 |
| 交易与合同 | FR-17~19 | `appointment`、`contract`、`order` | 预约时段互斥由 `active_slot` 唯一键表达（仅待确认/已确认持有占位键，终态置 NULL 释放时段，因此已取消/已拒绝的时段可被重新预约，FR-17）；预约时间须晚于当前时间；合同模板 + 信息自动填充生成，签约后状态流转与副本留存，合同详情仅合同双方与管理员可读（FR-18）；签约成功生成租赁订单并按期生成租金账单（FR-19，仅记录不对接支付） |
| 评价与消息 | FR-20、FR-21 | `review`、`notification` | 评价以租赁订单唯一约束保证"仅完成合同可评、一单一评"；关键事件统一经 `NotificationService` 站内信触达（5 秒内可见，轮询/长连接） |
| 后台管理 | FR-22~24 | `admin` | 用户禁用即时生效（JWT 黑名单）；审核操作全量写 `audit_log` 留痕（FR-23）；看板为只读聚合查询，按日/周/月分组统计（FR-24），含 AI 对话量与会话趋势；AI 对话审计可查看全站会话轨迹与工具链（NFR-05，见 4.4） |

## 四、AI 智能体层设计（项目特色）

### 4.1 组件结构

```

┌─────────┐   ┌──────────┐   ┌────────────────────────────┐   ┌───────────┐

│ 会话/记忆 │   │ 场景路由   │   │ 角色设定 · ReAct 规划 · 反思   │   │ 来源引用    │
└─────────┘   └──────────┘   │ 工具注册表（@Tool 注解扫描）    │   │ 免责声明    │

                    ┌────────────────────┼──────────────────────┐
                    ▼                    ▼                      ▼
```

### 4.2 核心机制

| 机制 | 设计 | 对应需求 |
| ---- | ---- | -------- |
| 会话路由 | 按 `scene`（找房助手 / 智能客服 / 合同解读）路由到不同角色设定与工具集；客服未命中知识库时礼貌转人工提示 | FR-12/13 |
| 工具注册表 | 业务方法以 `@Tool` 注解注册，Agent 运行时按需调用；新增工具只需注册定义，不改对话主流程（新增工具自动获得工具链留痕，见 4.4） | FR-12/15/16、NFR-09 |
| 记忆管理 | Redis 维护热会话滑动窗口（近 N 轮）+ 超长时摘要压缩；会话与消息全量落库（`ai_chat_session` / `ai_chat_message`）支持回溯 | FR-12 多轮追问 |
| 对话审计与工具留痕 | 每轮对话以 `role` 区分用户/助手/工具三类消息全量落库；工具调用额外记录 `tool_name`/`tool_args`/`tool_result`/`latency_ms`，助手回复记录 `token_count`；管理员经 `/admin/chats` 查看全站会话与逐步轨迹（详见 4.4） | NFR-05、FR-24 |
| RAG | 知识库切片检索（首版为关键词命中 + 计分，向量检索升级位 `vector_ref` 已预留）；回答强制附带来源引用；合同/资金类问题只允许知识库口径作答 | FR-13、NFR-05、风险 R2 |
| LLM 网关 | 三协议后端适配（openai-chat-completions / anthropic-messages / openai-responses），**三种协议的适配器全部自研实现**（不依赖 langchain4j 的厂商模型类）：均支持 Function Calling、多轮工具消息回填，且**同一轮内的正文与工具调用分别累积后合并**——模型普遍"先叙述再调工具"，按"有正文即丢弃工具调用"处理会导致工具永远不执行；端点、API Key、模型可配置，命名后端经 `AI_BACKEND` 一键切换 | 风险 R1、NFR-09 |
| AI 能力接入 | **全部 AI 能力均调用真实大模型**：对话走流式编排，四项分析（定价/检测/解读/识别填充）经统一的结构化调用层 `AiJsonClient`——优先以 `response_format=json_schema`（strict）由服务端强制约束返回结构（Schema 由目标返回类型经 `JsonSchemas` 生成），端点不支持该参数时退回"提示词 `AiPrompts` 声明字段 + 解析容错"，两种方式都对结果做字段与取值域校验；**未配置模型或调用失败一律返回 4001**，不提供任何规则/模拟兜底；模型未返回正文与工具调用时按失败上报（不伪造“没有生成有效回答”） | FR-08/12~16、风险 R1 |
| 流式输出 | SSE 逐 token 推送，首字 ≤ 3s | NFR-02 |
| AI 分析任务 | 定价建议、虚假房源检测、合同解读、识别填充为"请求 → 模型结构化分析 → 校验 → 结果落 `ai_analysis`"模式：代码侧只提供数据事实（同类样本统计、条款原文、房源字段）与结果校验（字段完整性、取值域、逐条覆盖），判断由模型给出；结果带依据与样本量，管理员保留最终裁决权 | FR-08/14/15/16 |

### 4.4 对话审计与工具调用留痕（NFR-05）

设计目标：管理员可查看**全站所有用户**的 AI 会话，并回放单会话的完整轨迹——人物（归属用户与角色）、多轮对话、工具使用（工具名 / 入参 / 返回 / 耗时）、RAG 引用与 token 用量，形态对齐主流 Agent 工具的 Trace 视图。日志只增不改，视图只读。

**数据模型（复用既有表，无新增表）**：`ai_chat_message` 以 `role` 区分三类消息——`1` 用户、`2` 助手、`3` 工具调用；工具消息写入 `tool_name` / `tool_args` / `tool_result` / `latency_ms`，助手消息写入 `token_count` 与整轮 `latency_ms`。两个 JSON 列落库前统一校验：合法且不超长原样保留，超长只留 `{truncated,preview}` 预览，非 JSON 包 `{raw}`，避免 MySQL 拒绝非法 JSON 或大结果撑爆消息表。助手消息正文取本轮流式增量的拼接，并以终止事件携带的正文兜底——部分协议只在终止事件里给完整正文（流式 delta 全程为空），若一律按增量落库会存下一条空白助手消息，审计视图随之失真。同一情况下正文还会**补走 delta 通道**推给前端（否则界面停在空白气泡，而只按 delta 取正文的调用方会误判为“模型没回答”），落库与推送口径保持一致。

**留痕点（两种引擎统一口径）**：

| 引擎 | 留痕方式 | 说明 |
| ---- | -------- | ---- |
| 工具调用留痕（LangChain4j） | `HousingToolProvider` 实现 `ToolProvider`，把每个 `@Tool` 方法的执行包装为"计时 → 执行 → 留痕 → 返回" | 用提供器而非改工具方法，使新增 `@Tool` 方法**自动**获得留痕能力（NFR-09）；会话号取自 `ToolExecutor.execute(…, memoryId)`，不依赖线程上下文 |
| 流式工具调用兜底（最后一道网） | `LlmAgent` 在每轮结束时读取本会话**实际执行过的工具名**（`HousingToolProvider` 记录）：**执行过工具就不重跑**；以下两类情况追加强化指令以**非流式**重跑一次（同一 Agent、同一会话记忆），再把完整回答切片回放为 delta：① 本轮一个工具都没执行且回答不像结论（找房未调 `searchHouses` 且回答过短 / 客服未调 `searchKnowledge` 因而没有来源）；② 本轮属于**可自愈的传输层故障**——限流（429）、5xx、超时、断连，或模型既没正文也没工具调用（推理占满预算、流被截断）。鉴权失败等 4xx 不重跑，直接如实报错 | 正常链路已由协议适配器保证（见 4.2"LLM 网关"）：工具真实执行过，短回答是模型的真实结论（如"暂无符合条件的房源"），重跑反而浪费一次调用；此兜底只覆盖传输异常/模型输出质量异常 |

**读模型与接口**：

| 端点 | 说明 | 需求 |
| ---- | ---- | ---- |
| `GET /admin/chats` | 全站会话分页列表：会话（场景/标题/转人工）+ 人物（昵称/账号/手机/角色）+ 规模（轮次/消息数/工具调用数/token）+ 最后一条消息预览；支持关键词（标题与用户三字段）、场景、转人工、用户 id 过滤 | NFR-05、FR-24 |
| `GET /admin/chats/{id}` | 单会话轨迹：会话与人物、当前生效引擎与角色设定原文、规模统计与工具使用明细、按 id 升序的逐步消息（含工具入参与返回、引用来源） | NFR-05 |
| `GET /admin/dashboard` | 在原看板基础上补充 AI 对话量：会话数、消息数、工具调用数、转人工会话数与会话新增趋势 | FR-24 |

列表的会话规模用一条 `GROUP BY session_id` 聚合查询批量取得（消息数/轮次/工具数/token/末条 id），再批量取末条消息做预览，避免逐会话查询造成 N+1。

**已知口径限制**：历史消息未逐条快照所用引擎/模型，故详情页的"当前生效引擎"标注为**查看时刻**的引擎值；系统同一时刻只有一个生效模型（配置驱动），跨模型的会话需结合配置变更时间人工判读。

### 5.1 规范约定

| 项 | 约定 |
| -- | ---- |
| 风格 | RESTful，前缀 `/api/v1`；资源名复数小写（如 `/api/v1/houses`） |

## 九、出错处理与日志

1. **全局异常处理器**：业务异常 → 统一错误码 + 中文提示；系统异常 → 5xxx 通用提示（不外泄堆栈），日志记录完整上下文；
2. **AI 失败链路**：未配置模型 / 模型调用失败 / 返回结构不合规 → 统一返回 4001 并附可读原因（前端提示重试），**不做规则或模拟兜底**；`response_format=json_schema` 被端点拒绝（4xx）→ 进程内记住该事实，后续分析改用提示词约束，不逐次重试；本轮未执行任何工具且回答不像结论、或本轮属可自愈传输层故障（空返回 / 限流 / 5xx / 超时）→ 非流式重跑一次（4xx 不重跑）；模型既无正文也无工具调用 → 4001 并附原因（不伪造回答）；客服未命中知识库 → 转人工提示；
3. **日志规范**：`操作审计日志`（audit_log 表，留痕审核/禁用等管理动作）+ `应用日志`（SLF4J 分级；AI 调用的 token 用量与延迟除落日志外，同步落 `ai_chat_message` 供 NFR-02 度量与后台对话审计查看）；工具留痕写库失败只告警，不中断对话主流程。
