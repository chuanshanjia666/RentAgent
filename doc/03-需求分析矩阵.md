## 一、什么是需求分析矩阵

需求分析矩阵（Requirements Analysis Matrix）是将系统需求按**统一编号、模块归属、优先级、涉及角色、验收标准**等维度组织成结构化表格的分析工具。其作用是：

1. **可追溯**：每条需求有唯一编号，可从需求追踪到设计、代码与测试用例；
2. **可排期**：通过优先级（MoSCoW 法）明确"先做什么、后做什么、不做什么"；
3. **可验收**：每条需求绑定验收标准，测试与答辩验收时逐条核对；
4. **防蔓延**：新需求必须进入矩阵并评估优先级，避免开发过程范围失控。

**优先级定义（MoSCoW 法）：**

| 级别 | 含义 | 交付要求 |
| ---- | ---- | -------- |
| P0（Must have） | 系统核心，缺失则业务闭环不成立 | 必须交付 |
| P1（Should have） | 重要但可短期降级运行 | 尽量交付，演示前必须完成 |
| P2（Could have） | 体验增强项 | 时间允许则交付 |
| P3（Won't have） | 本期明确不做 | 不开发（对应确认书范围外清单） |

## 二、需求获取方法

| 方法 | 应用方式 |
| ---- | -------- |
| 用户调研 | 对 5~10 名有租房经历的同学/朋友进行访谈，收集找房痛点 |
| 竞品分析 | 分析贝壳、自如、58 同城的房源发布、筛选、签约流程 |
| 场景分析 | 沿"找房 → 看房 → 签约 → 履约 → 退租"用户旅程逐环节挖掘需求 |
| AI 能力映射 | 将"重复沟通、模糊检索、条款理解"等痛点映射到智能体能力（对话、RAG、工具调用） |

## 三、用户角色与核心场景

| 角色 | 核心使用场景 |
| ---- | ------------ |
| 租客 | 用一句话描述需求让 AI 帮忙找房；筛选/收藏房源；预约看房；签约前让 AI 解读合同；咨询押金/退租政策 |
| 房东 | 发布房源；查看 AI 给出的定价建议；处理看房预约；管理在租订单 |
| 管理员 | 审核房源（AI 辅助识别虚假房源）；管理用户与评价；查看运营统计看板 |

## 四、功能需求矩阵

### 4.1 用户与权限模块

| 编号 | 需求名称 | 需求描述 | 角色 | 优先级 | 验收标准 |
| ---- | -------- | -------- | ---- | ------ | -------- |
| FR-01 | 用户注册 | 租客/房东通过手机号+验证码或账号密码注册，注册时选择角色 | 游客 | P0 | 注册成功自动登录并跳转对应角色首页；重复手机号注册给出提示 |
| FR-02 | 用户登录 | 支持账号密码登录，登录态采用 JWT 维护 | 全部 | P0 | 登录成功进入对应角色首页；密码错误 5 次锁定 10 分钟 |
| FR-03 | 实名认证 | 房东发布房源前须提交姓名+身份证号完成实名认证 | 房东 | P1 | 未认证房东无法进入房源发布页；认证信息加密存储 |
| FR-04 | 个人信息管理 | 查看/修改昵称、头像、联系方式；修改密码 | 全部 | P1 | 修改后新信息即时生效；密码修改后需重新登录 |

### 4.2 房源管理模块

| 编号 | 需求名称 | 需求描述 | 角色 | 优先级 | 验收标准 |
| ---- | -------- | -------- | ---- | ------ | -------- |
| FR-05 | 房源发布 | 房东填写标题、小区、户型、面积、租金、押付方式、设施、图片等信息发布房源 | 房东 | P0 | 必填项校验完整；发布成功后状态为"待审核" |
| FR-06 | 房源编辑与上下架 | 房东可修改房源信息、手动上架/下架 | 房东 | P0 | 编辑后重新进入待审核态；下架房源对租客不可见 |
| FR-07 | 房源审核 | 管理员审核房源，通过/驳回（附驳回理由） | 管理员 | P0 | 驳回后房东收到站内通知；仅"已通过"房源可被租客检索 |
| FR-08 | 房源信息智能识别 | 发布时上传实拍图，AI 自动识别户型/装修风格并辅助填写描述 | 房东 | P2 | 识别结果可一键填充且允许人工修改 |

### 4.3 房源检索与推荐模块

| 编号 | 需求名称 | 需求描述 | 角色 | 优先级 | 验收标准 |
| ---- | -------- | -------- | ---- | ------ | -------- |
| FR-09 | 多条件筛选 | 按区域、租金区间、户型、面积、朝向、设施组合筛选，支持排序 | 租客 | P0 | 筛选结果与条件完全匹配；分页加载正常 |
| FR-10 | 地图找房 | 以地图形式展示房源分布，点击标记查看房源卡片 | 租客 | P1 | 地图加载 ≤ 3 秒；拖动地图联动刷新房源 |
| FR-11 | 个性化推荐 | 基于浏览/收藏/咨询行为的个性化房源推荐 | 租客 | P1 | 首页推荐位展示；同一用户重复访问推荐结果趋于收敛 |

### 4.4 AI 智能体服务模块（项目特色）

| 编号 | 需求名称 | 需求描述 | 角色 | 优先级 | 验收标准 |
| ---- | -------- | -------- | ---- | ------ | -------- |
| FR-12 | AI 找房助手 | 对话式找房：智能体解析自然语言需求（预算/通勤/户型/偏好）→ 调用房源检索工具 → 返回房源卡片与推荐理由，支持多轮追问与调整条件 | 租客 | P0 | 10 条典型需求语句全部正确解析并返回有效房源；支持"再便宜一点""要近地铁"等增量修改 |
| FR-13 | 智能客服 | 基于 RAG 知识库（平台规则、租赁政策 FAQ）回答押金、退租、维修、违约等高频问题 | 全部 | P0 | 知识库覆盖 ≥ 50 条 FAQ；命中知识库的问题回答准确且附带来源；未命中时礼貌转人工 |
| FR-14 | 合同智能解读 | 签约前对电子合同条款逐条通俗化解释，标红风险条款（如高额违约金、单方涨租） | 租客 | P1 | 对含 3 处风险样例的测试合同全部命中并给出提示；解读内容注明"AI 生成，仅供参考" |
| FR-15 | 智能定价建议 | 房东发布房源时，智能体基于同小区/同户型历史成交与在租数据给出定价区间与建议 | 房东 | P1 | 建议包含区间、依据与数据样本量；无同类样本时明确告知数据不足 |
| FR-16 | 虚假房源检测（辅助审核） | 审核时 AI 对房源文本、图片与历史数据做一致性分析，输出风险分与疑点列表 | 管理员 | P2 | 风险分 ≥ 阈值的房源在审核列表置顶；管理员保留最终裁决权 |

### 4.5 交易与合同模块

| 编号 | 需求名称 | 需求描述 | 角色 | 优先级 | 验收标准 |
| ---- | -------- | -------- | ---- | ------ | -------- |
| FR-17 | 预约看房 | 租客选择日期时段发起看房预约，房东确认/拒绝，双方收到通知 | 租客 / 房东 | P0 | 时间段冲突时禁止重复预约；状态流转：待确认→已确认/已拒绝→已完成 |
| FR-18 | 在线签约 | 确认租赁意向后，系统基于模板生成电子合同，双方在线确认签约，AI 解读入口内嵌 | 租客 / 房东 | P0 | 合同自动填充双方信息与租赁条款；签约后合同状态与副本可查 |
| FR-19 | 订单与租金管理 | 生成租期与租金计划，记录每期租金支付状态，支持续租/退租申请 | 租客 / 房东 | P1 | 租金账单按期生成；退租申请走确认流程并更新房源状态 |

## 五、非功能需求矩阵

| 编号 | 类别 | 需求描述 | 度量 / 验收标准 | 优先级 |
| ---- | ---- | -------- | ---------------- | ------ |
| NFR-01 | 性能 | 常规页面与接口响应迅速 | 95% 接口响应 ≤ 2s（并发 50） | P0 |
| NFR-02 | AI 性能 | 对话体验流畅 | AI 回复首字延迟 ≤ 3s，采用流式输出 | P0 |
| NFR-03 | 安全 | 账号与数据安全 | 密码 BCrypt 加密；JWT 鉴权；接口防越权（水平/垂直）；防 SQL 注入/XSS | P0 |
| NFR-04 | 隐私合规 | 个人信息保护 | 身份证号等敏感字段加密存储；AI 上下文不外传用户隐私 | P0 |
| NFR-05 | AI 内容合规 | 生成内容可信可溯 | 合同/资金类问题强制引用知识库来源并声明"AI 生成仅供参考"；保留对话日志 | P0 |
| NFR-06 | 兼容性 | 多浏览器与移动浏览 | Chrome / Edge / Safari 最近两个大版本；页面响应式适配 ≥ 375px 宽度 | P1 |
| NFR-07 | 可用性 | 系统稳定运行 | 演示期可用率 ≥ 99%；核心接口异常有友好错误页 | P1 |
| NFR-08 | 可维护性 | 工程质量 | 分层架构；接口有 Swagger 文档；核心模块有单元测试 | P1 |
| NFR-09 | 可扩展性 | 智能体能力可插拔 | 新增智能体工具仅需注册工具定义，无需改动对话主流程 | P2 |
