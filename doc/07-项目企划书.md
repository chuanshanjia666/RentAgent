**项目要解决的问题**：传统租房平台只完成了"信息陈列"，没有完成"理解需求、辅助决策"——虚假房源泛滥、模糊需求难以表达、沟通成本高、合同看不懂、定价无依据。RentAgent 以大模型智能体（自然语言理解 + RAG + Function Calling 工具调用）重构"找房 → 看房 → 签约 → 履约"全链路体验。

## 二、项目背景与市场分析

### 2.1 行业背景

我国城镇租房人口规模已超过 2 亿，人口向中心城市流动、购房年龄推迟等趋势下租赁市场持续扩大，线上化平台已成主流渠道。但当前平台普遍存在五大痛点：

| 痛点 | 具体表现 | RentAgent 的应对 |
| ---- | -------- | ---------------- |
| 信息不对称 | 房源描述与实际不符、图片过度美化 | AI 虚假房源检测辅助审核（FR-16）+ 实名认证（FR-03）+ 全量审核机制（FR-07） |
| 匹配效率低 | 关键词筛选难以表达"通勤 30 分钟、预算 2500、采光好" | AI 找房助手自然语言找房（FR-12） |
| 沟通成本高 | 押金/退租/维修等高频问题反复人工咨询 | RAG 智能客服 7×24 应答（FR-13） |
| 合同门槛高 | 条款专业性强，租客难辨风险 | 合同智能解读、风险条款标红（FR-14） |
| 定价无依据 | 房东定价随意导致空置率偏高 | 智能定价建议（FR-15） |

### 2.2 市场趋势判断

1. **供给端**：大模型 API（GLM-4、GPT、通义、DeepSeek 等）已在生产环境稳定支持 Function Calling 与长上下文，按量计费使中小应用接入成本趋近于零；
2. **需求端**：年轻租客对对话式交互接受度高，"用一句话找一个家"符合主流交互习惯的演进方向；
3. **技术生态**：LangChain / Spring AI 等框架与向量数据库广泛商用，智能体工程化路径成熟、风险可控。

### 2.3 竞品分析

| 竞品类型 | 代表 | 优势 | 短板 | 与本项目关系 |
| -------- | ---- | ---- | ---- | ------------ |
| 综合租房平台 | 贝壳、自如、58 同城 | 房源量大、交易流程成熟 | AI 能力以传统推荐算法为主，缺乏对话式服务与交易闭环内的智能体 | 借鉴其业务流程范式 |
| 国际平台 | Zillow | 产品成熟、数据服务完善 | 本土化不足，同样缺少智能体深度融入 | 对标其信息展示体验 |
| AI 对话产品 | ChatGPT、智谱清言、Kimi | 自然语言交互体验好 | 无租赁领域业务数据与交易能力 | 验证了交互习惯的可迁移性 |
| 垂直智能体 | 电商客服、法律合同助手 | "领域知识 + 工具调用"模式已验证 | 未覆盖租赁全流程交易闭环 | 本项目将该模式移植到租赁场景 |

**差异化定位**：目前市场缺少"智能体不仅能对话，还能直接调用找房、预约、合同生成等业务工具完成交易闭环"的系统。RentAgent 的智能体是**带工具的业务角色**，而非套壳聊天窗口。

### 2.4 SWOT 分析

| | 有利 | 不利 |
| ---- | ---- | ---- |
| **内部** | **S 优势**：AI 能力与业务闭环深度融合的差异化设计；三端完整功能覆盖；团队具备 Java/Vue/Python 基础；原型与需求文档齐备、开发路径清晰 | **W 劣势**：团队 AI 工程经验有限；无真实房源与运营数据冷启动；课程项目周期内难以做大规模性能优化 |
| **外部** | **O 机会**：大模型 API 成本低廉且可平滑替换；"AI + 垂直行业"处于风口，答辩展示与衍生创作空间大；课程场景允许聚焦演示闭环 | **T 威胁**：大厂平台若快速跟进 AI 功能形成降维打击；API 收费政策或稳定性变化；生成式 AI 内容合规要求趋严 |

**策略结论**：以差异化特色（智能体 + 交易闭环）为核心，用成熟框架与可替换模型网关控制技术风险，聚焦"可演示、可验收"的最小闭环，规避与成熟平台的正面规模竞争。

## 三、产品与服务方案

### 3.1 产品定位与用户价值

| 角色 | 核心主张 | 对应核心需求 |
| ---- | -------- | ------------ |
| 租客 | 像聊天一样找到真实房源，签约前有人（AI）帮你把关 | FR-09/10/11/12/13/14/17/18/20/25 |
| 房东 | 高效发布管理房源，AI 帮你定价、减少空置 | FR-05/06/08/15/17/19 |
| 管理员 | AI 辅助审核提升效率，看板掌握全局 | FR-07/16/22/23/24 |

### 3.2 功能架构

系统按七大功能模块组织，共 25 项功能需求（P0×10 / P1×12 / P2×3，详见《03-需求分析矩阵》v1.1）：

```
┌────────────────────────────────────────────────────┐
│                租客端 / 房东端 / 管理端              │
├──────────┬──────────┬──────────┬──────────────────┤
│ 用户与权限 │ 房源管理  │ 检索与推荐 │  AI 智能体服务   │
│ FR-01~04  │ FR-05~08 │ FR-09~11  │  FR-12~16（特色） │
├──────────┼──────────┼──────────┴──────────────────┤
│ 交易与合同 │ 评价与消息 │ 后台管理                    │
│ FR-17~19  │ FR-20/21  │ FR-22~24                   │
└──────────┴──────────┴────────────────────────────┘
```

**P0 需求构成 MVP 业务闭环**：注册登录 → 发布房源 → 审核 → 筛选/搜索 → AI 找房 → 智能客服 → 预约看房 → 在线签约。

### 3.3 AI 特色能力（项目亮点）

| 能力 | 说明 | 优先级 |
| ---- | ---- | ------ |
| AI 找房助手 | 自然语言 → 结构化查询 → 调用房源检索工具 → 返回房源卡片与推荐理由，支持多轮增量调整 | P0 |
| 智能客服 | RAG 知识库问答（≥50 条 FAQ），回答附来源，未命中转人工 | P0 |
| 合同智能解读 | 条款逐条通俗化解释，风险条款标红提示（含"AI 生成，仅供参考"声明） | P1 |
| 智能定价建议 | 基于同区域/同户型样本给出定价区间、依据与样本量，无样本时明确告知 | P1 |
| 虚假房源检测 | 文本/图片一致性分析输出风险分与疑点列表，风险分 ≥70 置顶，管理员保留最终裁决权 | P2 |

**AI 工程实现路径**：大模型 API（智谱 GLM-4，兼容 OpenAI 协议可替换）+ Function Calling 工具集（房源检索/预约/合同生成/定价分析）+ RAG（房源与政策知识库向量化检索）+ 多轮对话记忆；模型网关层抽象支持一键切换备用模型。

### 3.4 原型进展

22 页高保真原型已以可运行 React 单页应用形式实现（`prototype/` 目录，页面与 FR 编号一一对应），覆盖三端全部页面与 5 个关键状态页，AI 对话、风险条款解读、审核工作台等核心交互均可点击演示，可直接用于答辩与评审（见《04-原型工具使用方法》v1.2 与 prototype/README.md）。原型采用 React 仅为演示载体，正式开发技术栈以下述第五章为准。

## 四、商业模式与运营规划（设想）

> 本项目为课程设计项目，本节为**模式设想与可行性论证**，本期不实现任何收费功能。

### 4.1 价值主张

- 对租客：降低找房与决策成本（时间、沟通轮次、踩坑概率）；
- 对房东：提高成交转化、降低空置期；
- 对平台：AI 承接高频重复咨询与初审工作，降低人工客服与审核成本。

### 4.2 可持续的盈利模式设想（远期）

| 模式 | 内容 | 依据 |
| ---- | ---- | ---- |
| 交易服务费 | 按成交合同收取小额服务费 | 平台撮合交易闭环成立后自然延伸 |
| 房东增值服务 | 房源置顶曝光、智能定价 Pro 版、数据报告 | 房东对去化速度付费意愿明确 |
| AI 能力输出 | 智能客服/合同解读以 SaaS 形式输出给中小中介 | 智能体架构天然可插拔（NFR-09） |

### 4.3 运营与推广策略（课程场景）

1. **种子用户**：面向本校及周边有租房经历的同学开展访谈（需求调研已纳入《03-需求分析矩阵》第二节）与试用；
2. **演示物料**：以可点击原型 + 演示剧本（5 分钟走完租客/房东/管理三条线）作为主要展示载体；
3. **内容运营**：知识库 FAQ 随试用量持续扩充，作为智能客服命中率的迭代依据（FR-13 验收：准确率 ≥ 90%）。

## 五、技术方案

### 5.1 总体架构（四层 B/S 架构，前后端分离）

```
┌─────────────────────────────────────────────────────┐
│  表现层：Vue 3 + Element Plus 租客端 / 房东端 / 管理端  │
├─────────────────────────────────────────────────────┤
│  业务层：Spring Boot 3 RESTful API                    │
│   用户权限 · 房源管理 · 预约签约 · 订单评价 · 后台管理    │
├─────────────────────────────────────────────────────┤
│  智能体层（Agent Layer）                              │
│   LLM 网关 ── 意图识别 ── 记忆管理                     │
│   工具集：房源检索 / 预约 / 合同生成 / 定价分析          │
│   RAG：房源知识库 · 合同知识库 · 租赁政策 FAQ           │
├─────────────────────────────────────────────────────┤
│  数据层：MySQL 8（业务库）· Redis 7（缓存/会话）        │
│         向量检索（Redis Stack / PGVector）             │
└─────────────────────────────────────────────────────┘
```

### 5.2 技术选型（与《02-项目最终确认书》一致）

| 层次 | 选型 | 理由 |
| ---- | ---- | ---- |
| 前端 | Vue 3 + Vite + Element Plus + Pinia + ECharts | 生态成熟、组件库丰富、便于团队分工 |
| 后端 | Spring Boot 3.x + MyBatis-Plus | 国内主流企业级框架，开发效率高 |
| AI 接入 | 智谱 GLM-4 API（兼容 OpenAI 协议） | 按量计费成本可控，可平滑替换 |
| 智能体框架 | Spring AI / LangChain4j | Function Calling、记忆、RAG 工程化封装 |
| 数据库 | MySQL 8 + Redis 7 + 向量检索（Redis Stack / PGVector） | 业务 + 缓存 + 向量的经典组合，复用度高 |
| 安全 | JWT + RBAC + HTTPS + BCrypt | 满足多角色权限隔离与个人信息保护 |
| 部署 | Docker Compose 单机部署 | 课程项目运维成本最低 |

> 说明：已建成的 React 原型（prototype/）仅为快速演示载体，不构成对前端选型的变更；如团队决议改用 React 开发正式系统，须按《02-项目最终确认书》第九条走变更流程。

### 5.3 安全与合规设计

- 密码 BCrypt 加密、JWT 鉴权、接口防越权、防 SQL 注入/XSS（NFR-03）；
- 身份证号等敏感字段加密存储，AI 上下文不外传用户隐私（NFR-04）；
- AI 生成内容强制引用知识库来源并声明"AI 生成，仅供参考"，保留对话日志（NFR-05）；
- 每日数据备份与恢复预案（NFR-10）。

## 十、预期成果与验收标准

### 10.1 交付物清单

1. 可运行的三端 Web 系统（P0 闭环完整可用，Docker Compose 一键部署）；
