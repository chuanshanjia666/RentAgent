# RentAgent 项目技术背景介绍

> 项目名称：RentAgent —— 基于 AI 智能体的房屋租赁系统
> 文档版本：v1.0
> 编写日期：2026-09-03

---

## 一、行业背景与业务痛点

住房租赁是民生领域的高频刚需场景。根据住建部及主流租房平台公开数据，我国城镇租房人口规模已超过 2 亿人，且随着人口向中心城市持续流动、购房年龄推迟等趋势，租赁市场规模仍在扩大。与传统"中介门店"模式相比，线上化租房平台已成为主流渠道，但当前平台普遍存在以下痛点：

| 痛点 | 具体表现 |
| ---- | -------- |
| 信息不对称 | 房源描述与实际不符、图片过度美化，租客筛选成本高 |
| 虚假房源泛滥 | 部分中介以低价假房源引流，平台人工审核滞后 |
| 匹配效率低 | 传统关键词 + 筛选条件的搜索方式，难以表达"通勤 30 分钟内、预算 2500、采光好"这类模糊、复合的需求 |
| 沟通成本高 | 租客咨询需反复与中介/房东往返沟通，常见问题（押金、违约、维修）重复率高 |
| 合同理解门槛高 | 租赁合同条款专业性强，租客签约前难以识别风险条款 |
| 决策支持缺失 | 房东缺乏定价参考，定价随意导致空置率偏高 |

这些痛点的共性在于：**平台只完成了"信息陈列"，没有完成"理解需求、辅助决策"**。这正是大语言模型（LLM）与 AI 智能体技术能够发挥价值的地方。

## 二、AI 智能体技术的发展现状

### 2.1 从大模型到智能体

- **大语言模型（LLM）**：以 GPT、GLM、Qwen、DeepSeek 等为代表的大模型具备了自然语言理解、推理与生成能力，为"用自然语言完成复杂任务"提供了基础。
- **检索增强生成（RAG）**：将平台内的房源数据、合同模板、政策 FAQ 等知识向量化后按需检索，注入模型上下文，使回答"有据可依"，显著抑制幻觉，是私有数据与大模型结合的主流方案。
- **Function Calling（工具调用）**：大模型可以按预定义的函数规范发起结构化调用，由系统执行真实操作（如查询数据库、创建订单）后把结果回传给模型，使模型从"能说"进化为"能做"。
- **AI 智能体（Agent）**：在 LLM 之上叠加角色设定、记忆、工具集与任务规划能力，能够围绕用户目标自主进行"理解 → 规划 → 调用工具 → 反思 → 交付"的多步闭环。

### 2.2 技术成熟度判断

2024 年以来，主流大模型厂商（OpenAI、Anthropic、智谱 AI、阿里通义等）均已在生产环境稳定支持 Function Calling 与长上下文；LangChain、LlamaIndex 等框架大幅降低了 Agent 开发门槛；向量数据库（Milvus、Redis Stack、PGVector 等）已广泛商用。**在本项目中引入 AI 智能体，技术链路完整、风险可控，已具备工程落地条件。**

## 三、国内外相关应用现状

| 领域 | 代表实践 | 与本项目的关系 |
| ---- | -------- | -------------- |
| 通用租房平台 | 贝壳、自如、Zillow（美国） | 提供了成熟的租赁业务流程范式（房源 → 搜索 → 看房 → 签约 → 履约），但 AI 能力仍以传统推荐算法为主 |
| AI 对话产品 | ChatGPT、智谱清言、Kimi | 验证了自然语言交互的用户接受度，但缺乏租赁领域的业务数据与交易能力 |
| 垂直领域智能体 | 电商客服机器人、法律合同助手、AI 导购 | 证明了"领域知识 + 工具调用"模式在垂直场景的商业价值，本项目将其移植到租赁场景 |

**结论**：目前市场上尚缺少"把租赁业务全流程与 AI 智能体深度融合"的系统——即智能体不仅能对话，还能直接调用找房、看房预约、合同生成等业务工具完成交易闭环。这是 RentAgent 的差异化定位。

## 四、本项目的技术方案概述

### 4.1 总体架构

系统采用前后端分离的 B/S 架构，自上而下分为四层：

```
┌─────────────────────────────────────────────────┐
│  表现层：Vue 3 + Element Plus 租客端 / 房东端 / 管理端  │
├─────────────────────────────────────────────────┤
│  业务层：Spring Boot 3 RESTful API                │
│   用户权限 · 房源管理 · 预约签约 · 订单评价 · 后台管理   │
├─────────────────────────────────────────────────┤
│  智能体层（Agent Layer）                          │
│   LLM 网关 ── 意图识别 ── 记忆管理                  │
│   工具集：房源检索 / 预约 / 合同生成 / 定价分析        │
│   RAG：房源知识库 · 合同知识库 · 租赁政策 FAQ          │
├─────────────────────────────────────────────────┤
│  数据层：MySQL 8（业务库）· Redis 7（缓存/会话）      │
│         向量库（房源/知识 Embedding 检索）            │
└─────────────────────────────────────────────────┘
```

### 4.2 技术选型及理由

| 层次 | 技术 | 选型理由 |
| ---- | ---- | -------- |
| 前端 | Vue 3 + Vite + Element Plus + Pinia | 生态成熟、组件库丰富，适合快速构建管理型多端界面 |
| 后端 | Spring Boot 3.x + MyBatis-Plus | 国内主流企业级框架，开发效率高，便于团队分工 |
| AI 接入 | 智谱 GLM-4 大模型 API（可替换为其他兼容 OpenAI 协议的模型） | 通过 API 接入，无需自训练模型，成本可控、可平滑替换 |
| 智能体框架 | Spring AI / LangChain4j | 提供 Function Calling、记忆、RAG 的工程化封装 |
| 向量检索 | Redis Stack / PGVector | 与现有基础设施复用度高，避免额外运维向量数据库集群 |
| 数据库 | MySQL 8 + Redis 7 | 关系型业务数据 + 高频缓存/会话的经典组合 |
| 安全 | JWT 鉴权 + RBAC 权限模型 + HTTPS | 满足多角色权限隔离与个人信息保护要求 |

### 4.3 AI 智能体的核心能力设计

1. **AI 找房助手**：租客用自然语言描述需求（预算、通勤、户型、偏好），智能体解析为结构化查询条件，调用房源检索工具返回匹配房源并给出推荐理由。
2. **智能客服**：基于租赁政策与平台规则知识库（RAG）自动应答押金、退租、维修、违约等高频问题，7×24 小时在线。
3. **合同智能解读**：签约前对合同条款进行风险提示与通俗化解释，辅助租客识别不公平条款。
4. **智能定价助手**：为房东提供同区域、同户型房源的价格分析，给出定价区间建议。
5. **虚假房源检测（辅助审核）**：对房源文本与图片信息进行一致性、异常特征分析，辅助管理员提升审核效率。

## 五、项目建设的意义

1. **业务价值**：以"对话即服务"重构找房体验，缩短"需求表达 → 房源匹配 → 签约成交"的链路；降低平台人工客服与审核成本。
2. **技术价值**：完整实践"大模型 + RAG + Function Calling + 业务系统"的智能体工程化路径，形成可复用的智能体接入架构。
3. **学习价值**：覆盖前后端分离开发、数据库设计、权限安全、AI 应用工程等软件工程全栈知识点，是 AI 时代应用型系统开发的典型练兵场。

## 六、可行性分析

| 维度 | 分析结论 |
| ---- | -------- |
| 技术可行性 | 大模型 API、RAG、Function Calling 均有成熟框架与文档支撑；团队具备 Java/Web 基础，学习曲线平缓 |
| 经济可行性 | 采用按量计费的大模型 API，开发与演示阶段成本极低；服务器可用单台云主机承载 |
| 操作可行性 | 用户以自然语言交互，无额外学习成本；管理员沿用可视化后台 |
| 法律与合规 | 生成式 AI 服务遵循平台内容规范，合同模板来源合法，用户个人信息按《个人信息保护法》最小化收集 |
