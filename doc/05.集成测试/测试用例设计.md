## 一、测试策略与分层

集成测试的目的是验证**单元测试用替身无法证明的部分**：

| 只能在此层验证的事物 | 原因 |
| -------------------- | ---- |
| 唯一键约束引发的业务码（预约时段 3001、一单一评 3005、一合同一订单、收藏幂等） | 单测只能注入 `DuplicateKeyException`，不能证明约束真的建在库上 |
| MyBatis-Plus 动态 SQL（`JSON_CONTAINS` 设施筛选、`likeRight` 户型前缀、`DATE_FORMAT` 聚合看板、逻辑删除） | 只有真 MySQL 才能验证生成的 SQL 语义 |
| Redis 语义（验证码 5 分钟、失败 5 次锁定 10 分钟） | TTL 与自增原子性属缓存实现行为 |
| 鉴权链路的真实 HTTP 表现（非法 token → HTTP 401；越权 → body `code=1007`） | 过滤器 + 拦截器 + 切面的组合行为 |
| 跨模块业务闭环（发布→审核→上架→预约→签约→订单→账单→退租→评价；AI 会话→工具留痕→审计） | 端到端状态一致性 |
| 真实模型通道的工具调用与引用来源（模型是否真的调用了检索/知识库工具） | 只有真模型才有工具调用链，须走真 Key |
| 未配置模型时的硬报错（4001）与"零兜底"约束 | 反向验证：任何 AI 接口在无模型时返回结果都说明兜底被重新引入 |

策略：**单条命令、带退出码的断言脚本** `scripts/ci-smoke.sh`（130 条断言）作为集成门禁，
与 CI 作业共用同一脚本，保证"本地怎么跑、流水线就怎么跑"。

### 1.1 与人工排障脚本的关系

`scripts/smoke.sh` 是人工排障用的**打印版**（只看不判，不返回失败状态）；
`scripts/ci-smoke.sh` 是**断言版**：每条断言计入通过/失败，任一失败即 `exit 1`，
可直接作为流水线门禁。两者流程与顺序一致，便于互相印证。

### 2.1 启动就绪判据（空库首启必读）

后端**接口可用 ≠ 数据可用**：`DataInitializer` 是 `CommandLineRunner` 且 `run()` 为 `@Transactional`，
Web 端口与数据库连接池都先于种子数据提交就绪（本机实测窗口约 0.57 秒，CI 冷容器下可达数秒）。
在窗口内登录会得到 `1002`（账号尚不存在），进而使所有依赖登录态的断言连锁失败。

因此就绪判据必须**查库**而非仅探端口：`scripts/ci-smoke.sh` 开头的 `wait_for_seed()` 会轮询
不鉴权的 `/houses?size=1`，直到返回演示房源（默认最多等 90 秒）再开始断言；流水线侧同样以该判据等待。
**不要用"反复尝试登录"当就绪探测**——登录失败会计入 Redis 失败计数（5 次锁定 10 分钟），会把演示账号锁住。

### 2.2 可重复性设计

集成脚本需支持在同一套环境上反复执行（本地排障时很常见），因此：

- 房源、合同、订单、会话等数据**每次运行新建**，不做全局计数断言（如"房源总数=9"）；
- 断言改为**相对口径**（如"账单期数 = 租期整月数"、"未读通知 ≥ 1"）；
- **模型输出不断言具体文案**：只断言结构性事实（是否非空、是否真的调用了工具、字段类型与取值域、引用条数），避免模型措辞变化造成假失败；
- 预约时段按"当前时间 + 随机天 + 随机分钟"生成，避免与历史运行撞唯一键；
- 登录失败计数用每次运行唯一的用户名，避免触发"5 次锁定"掩盖断言；
- 注册用时间戳派生的手机号，避免"手机号已注册"。

## 三、集成用例清单（130 条断言 / 11 组 + 1 组反向门禁）

用例编号 `IT-<组>-<序>`；`预期` 中的数字为统一响应体 `code`（除注明 HTTP 状态码处）。
全部断言由 `scripts/ci-smoke.sh` 自动执行（真实模型口径）。

另有 1 组**反向门禁**独立成脚本 `scripts/ci-no-model-check.sh`（6 条断言）：在同一套数据库上另起一个
**不注入模型凭据**的实例，验证"未配置模型时 AI 能力一律硬报错"——AI 对话、定价、识别填充、合同解读、
引擎探针全部必须返回 `4001`；任何一项返回 `code=0` 即判定"兜底实现被重新引入"，门禁失败。

## 五、FR-12 自然语言解析判分表（真实模型口径）

**结果为 2026-09-17 在演示数据集上的实测值**（数据来源：`GET /admin/chats/{id}` 的工具链留痕与助手回复文本；
每条语句建独立会话）：

| -- | -------- | ---------------- | ------------------ | ---- |
| 1 | 预算2500以内，要一居室，近地铁 | `searchHouses` ×1 | 返回 2 套（1900/2300 元/月）并给出逐套推荐理由 | ✅ |
| 2 | 想找二居室，预算3500 | `searchHouses` ×1 | 返回匹配房源并说明取舍 | ✅ |
| 3 | 三居室，不要太贵，2000以内 | `searchHouses` ×8 | 无精确匹配 → 说明原因并给出放宽建议（迭代检索条件） | ✅ |
| 4 | 近地铁的1室，价格1800以下 | `searchHouses` ×8 | 无匹配 → 给出放宽条件建议 | ✅ |
| 5 | 高新园区有没有2000左右的房子 | `searchHouses` ×2 | 返回匹配房源 | ✅ |
| 6 | 帮我找软件园附近的房子 | `searchHouses` ×3 | 按区域/关键词检索并给建议 | ✅ |
| 7 | 2000到3000之间，两居室 | 0~1 次（两次运行不同） | 一次直接放宽到 4000 元返回 2 套并解释；另一次先追问澄清 | ⚠️ 同一语句存在"追问/放宽"两种走向（见改进项 1） |
| 8 | 有没有1500的单间 | `searchHouses` ×3 | 无匹配 → 放宽建议 | ✅ |
| 9 | 预算100万，要别墅 | `searchHouses` ×5 | 识别为超预算/非平台房源 → 说明并给替代建议（原规则引擎会误解析为"100 元"） | ✅ |

结论：**10 条语句全部被正确理解并给出可用回应**，其中 8 条真的调用了房源检索工具；相比原规则引擎，
模型在区间（"2000到3000"）、单位（"100万"）、同义表达（"单间/两居"）等语义上不再有硬性盲区。

改进项（作为后续迭代输入）：

1. 同一语句可能"直接放宽检索"或"先追问"，建议在系统提示词中固定策略（如"无匹配时先放宽一次并说明，再追问"）；
2. **服务城市口径**：无上文时模型会臆测城市（实测出现"上海"），应在系统提示词中声明平台当前服务城市（大连）与数据范围；
3. 多次检索（最多 8 次）会增加首字与总耗时，可提示模型减少无效重试（先合并条件再查一次）；
4. 增量修改（"再便宜一点"）依赖同一会话上下文，前端已按会话续聊；建议补充"多轮上下文"的专项评测用例（见 §七 遗留项 8）。
