## 一、测试策略与分层

集成测试的目的是验证**单元测试用替身无法证明的部分**：

| 只能在此层验证的事物 | 原因 |
| -------------------- | ---- |
| 唯一键约束引发的业务码（预约时段 3001、一单一评 3005、一合同一订单、收藏幂等） | 单测只能注入 `DuplicateKeyException`，不能证明约束真的建在库上 |
| MyBatis-Plus 动态 SQL（`JSON_CONTAINS` 设施筛选、`likeRight` 户型前缀、`DATE_FORMAT` 聚合看板、逻辑删除） | 只有真 MySQL 才能验证生成的 SQL 语义 |
| Redis 语义（验证码 5 分钟、失败 5 次锁定 10 分钟） | TTL 与自增原子性属缓存实现行为 |
| 鉴权链路的真实 HTTP 表现（非法 token → HTTP 401；越权 → body `code=1007`） | 过滤器 + 拦截器 + 切面的组合行为 |
| 跨模块业务闭环（发布→审核→上架→预约→签约→订单→账单→退租→评价；AI 会话→工具留痕→审计） | 端到端状态一致性 |
| 无模型 Key 时的降级路径（规则引擎、知识库检索、转人工） | 演示环境必备路径 |

策略：**单条命令、带退出码的断言脚本** `scripts/ci-smoke.sh`（121 条断言）作为集成门禁，
与 CI 作业共用同一脚本，保证"本地怎么跑、流水线就怎么跑"。

### 1.1 与人工排障脚本的关系

`scripts/smoke.sh` 是人工排障用的**打印版**（只看不判，不返回失败状态）；
`scripts/ci-smoke.sh` 是**断言版**：每条断言计入通过/失败，任一失败即 `exit 1`，
可直接作为流水线门禁。两者流程与顺序一致，便于互相印证。

## 二、测试环境与数据前提

| 项目 | 要求 |
| ---- | ---- |
| 数据库 | MySQL 8.0（`rentagent` 库，先执行 `docker/mysql-init/01_schema.sql` 建 18 张表） |
| 缓存 | Redis（验证码 / 登录失败计数） |
| 后端 | JDK 17 运行 `server/target/rentagent-server-1.0.0.jar`，监听 8080 |
| 种子数据 | 空库启动时由 `DataInitializer` 自动灌入：5 个账号、8 套房源、12 篇知识库文档、历史成交与收藏 |
| 演示账号 | `xiaochen/123456`（租客）、`lilandlord/123456`（已实名房东）、`wanglandlord/123456`（未实名房东）、`admin/123456`（管理员）、`historyuser`（禁用） |
| 验证码 | 演示固定码 `246810`（`rentagent.captcha-dev-code`） |
| AI 通道 | **不注入任何模型 Key**，后端自动降级规则引擎；本文件的 AI 断言均按规则引擎口径编写 |
| 依赖工具 | `curl`、`jq`、GNU `date`（`date -d`）；查询串含中文处统一由 `curl --data-urlencode` 编码 |

### 2.1 可重复性设计

集成脚本需支持在同一套环境上反复执行（本地排障时很常见），因此：

- 房源、合同、订单、会话等数据**每次运行新建**，不做全局计数断言（如"房源总数=9"）；
- 断言改为**相对口径**（如"账单期数 = 租期整月数"、"未读通知 ≥ 1"）；
- 预约时段按"当前时间 + 随机天 + 随机分钟"生成，避免与历史运行撞唯一键；
- 登录失败计数用每次运行唯一的用户名，避免触发"5 次锁定"掩盖断言；
- 注册用时间戳派生的手机号，避免"手机号已注册"。

## 五、FR-12 自然语言解析判分表

规则引擎（无 Key 降级通道）的解析口径来自 `MockAgent.findHouseReply`：
预算 = 首个满足 300~100000 的 3~5 位数（不满足下限则继续向后寻找）；户型 = 首个 `[一二三1-3][居室]`；
通勤 = 是否含「地铁」；预算/户型/通勤三者皆未解析出时，退化为"前 20 字整句"关键词检索。

下表 10 条为验收用典型语句，**解析条件与检索结果均为 2026-09-17 在演示数据集上的实测值**
（数据来源：`GET /admin/chats/{id}` 的 `toolArgs` 留痕与助手回复文本）：

| 序 | 输入语句 | 实测解析条件 | 检索结果 | 判定 |
| -- | -------- | ------------ | -------- | ---- |
| 1 | 预算2500以内，要一居室，近地铁 | `maxRent=2500, layout=1室, subway=true` | 命中并返回推荐列表 | ✅ 已纳入 CI（IT-9-02~05） |
| 2 | 想找二居室，预算3500 | `maxRent=3500, layout=2室` | 命中并返回推荐列表 | ✅ 解析正确 |
| 3 | 三居室，不要太贵，2000以内 | `maxRent=2000, layout=3室` | 解析正确；演示数据无 ≤2000 的三居 → 返回放宽条件建议 | ✅ 解析正确（结果为空属数据约束） |
| 4 | 近地铁的1室，价格1800以下 | `maxRent=1800, layout=1室, subway=true` | 同上（无 ≤1800 的一居） → 放宽建议 | ✅ 解析正确 |

| 7 | 2000到3000之间，两居室 | `maxRent=2000`（区间取首个数字）、`layout=null`（「两居」不在词表） | 命中并返回推荐列表 | ⚠️ 改进项 1、2 |

| 9 | 预算100万，要别墅 | 预算为 `null`（"100" 低于 300 下限被跳过，且无"万"换算） → 退化为整句关键词检索 | 无命中 → 放宽建议 | ⚠️ 改进项 3 |

结论：**预算/户型/地铁三类核心条件的解析在 10 条语句上全部符合预期**（第 5、6、7、8、9、10 条的偏差
集中在"区域/区间上限/单位/同义词/上下文"这些更细的语义上，不影响"结构化条件 → 检索 → 推荐理由"主链路）。

改进项（作为后续迭代输入，当前演示口径已在表中如实标注）：

1. 预算区间语句取上限（"2000到3000" → 3000）；
2. 户型词表补充「两居 / 单间 / 一居」等同义表达；
3. 金额单位识别（"100万" → 1000000），并明示 300 元下限的提示文案；
4. 规则引擎引入会话级条件记忆（LLM 通道已通过 `memoryId` 携带历史，规则引擎缺此能力）；
5. 区域名解析（接入行政区词表，命中后填充 `district`）；
6. 无结构化条件时的关键词改为分词提取（当前为整句 LIKE，命中率低）；
7. 条件过严导致空结果时，回复中显式说明"已按 X 条件检索"（当前多条件命中样本为 0 时直接给放宽建议）。
